## Задания, где правильное решение может быть отклонено

### 1. P1 — Imos Sweep: неверный эталон

Условие задаёт **включительные** интервалы:
`n=5 updates=(0,2,2),(1,3,3),(3,4,1)`.
После обновлений массив равен **`[2,5,5,4,1]`**, максимум — **5**.
Во всех трёх стадиях урока записано **4**. Этот же ошибочный ответ
встроен в `verificationCases` и исполняемый `verificationSource`.

Общая корректная реализация включительных обновлений подана непосредственно
в поставляемый Rust harness. Он завершается с `PRIVATE CASE 1 FAILED`.
Ошибка затрагивает объяснение на сайте и проверку задания в приложении.

Исправление: эталон 5, согласованные примеры и harness; затем новая версия
Algorithms CoursePack. Проверить все повторения примера, а не только поле
`expectedAnswer`.

[Урок](https://crabrix.com/learn/algorithms/algorithm.imos-sweep.challenge) ·
[Исходник](https://github.com/sergii-ziborov/crabrix-courses/blob/52b6751/courses/algorithms/lessons/algorithm.imos-sweep.challenge.json#L7) ·
[Проверка](https://github.com/sergii-ziborov/crabrix-courses/blob/52b6751/courses/algorithms/checks/algorithm.imos-sweep.challenge.json)

### 2. P1 — Complement Lookup: допустимая пара отклоняется

Для `[6,4,9,7] target=13` подходят и **`0,3`** (`6+7`), и
**`1,2`** (`4+9`). Условие не задаёт выбор между ними.
Harness принимает только строку `1,2`.

Воспроизведено отклонение общей реализации с ожидаемой сложностью O(n),
возвращающей допустимую пару с минимальным левым индексом.
Это не следствие медленного перебора или неправильной суммы.

Исправление: проверять допустимость пары либо явно определить порядок
выбора и поведение при отсутствии пары. Эталонные строки должны следовать
этому контракту во всех тестах.

[Урок](https://crabrix.com/learn/algorithms/algorithm.complement-lookup.challenge) ·
[Проверка](https://github.com/sergii-ziborov/crabrix-courses/blob/52b6751/courses/algorithms/checks/algorithm.complement-lookup.challenge.json)

### 3. P1 — List Intersection: во входе потеряна идентичность узлов

Видимый ввод:
`A=4->1->8->4->5; B=5->6->1->8->4->5`, эталон **8**.
Значения узлов не сообщают, какие из них являются одним и тем же объектом.

Построены два графа с **точно такой же сериализацией**:

- Общий хвост начинается с `8`: ответ 8.
- Общий хвост начинается с `1`: ответ 1.

Можно также построить два полностью независимых списка с теми же значениями.
Следовательно, правильный ответ невозможно однозначно вывести из входа.
Сравнение равных значений не заменяет пересечение по идентичности узла.

Исправление: задавать общие node ID, отдельный общий хвост либо `skipA` и
`skipB`; показать соответствующую структуру входа и проверить оба случая.

[Урок](https://crabrix.com/learn/algorithms/algorithm.list-intersection.challenge) ·
[Исходник](https://github.com/sergii-ziborov/crabrix-courses/blob/52b6751/courses/algorithms/lessons/algorithm.list-intersection.challenge.json)

### 4. P2 — Monotonic Decreasing Stack: «предыдущие дни» и сегодняшний день

Условие просит число последовательных **earlier days** с ценой не выше
сегодняшней. Для первого дня таких дней 0. Эталон включает сегодняшний день:
`1,1,1,2,1,4,6` вместо буквального `0,0,0,1,0,3,5`.
Та же разница есть в скрытом случае `[10,20,15]`: `1,2,1` против `0,1,0`.

Исправление: назвать это stock span **включая сегодняшний день**, сохранить
стандартные эталоны и согласовать все три стадии урока.

[Урок](https://crabrix.com/learn/algorithms/algorithm.monotonic-decreasing-stack.challenge)

### 5. P2 — Reservoir Sampling: не определён смысл случайного выбора

Даны значения `[10,20,30,40]` и choices `[0,1,1,3]`, но не правило замены.
При равномерном выборе из `0..=i` обе схемы являются равномерным
одноэлементным reservoir sampling:

| Правило замены | Видимый результат | Скрытый случай `[5,6,7]`, choices `[0,0,2]` |
| --- | --- | --- |
| `choice == 0` | 10 | 6 |
| `choice == i` | 40 | 7 |

Проверка требует вторую схему. Без явно заданного правила первая корректная
схема выглядит для ученика ошибкой.

Исправление: определить диапазон выбора, индексацию и точное условие замены;
добавить пошаговый разбор choices.

[Урок](https://crabrix.com/learn/algorithms/algorithm.reservoir-sampling.challenge)

## Противоречия в объяснениях и ответах

### 6. P2 — Pinning Intuition: пример не демонстрирует обещанную неподвижность

Вопрос про `Pin<&mut String>` требует ответ **Stable location**.
Однако `String: Unpin`, и переместить значение через такой Pin можно
полностью безопасным Rust. Контрпример с `Pin::into_inner` и `mem::take`
компилируется и выполняется. Само объяснение уже упоминает исключение Unpin,
но вопрос и верхняя подпись инфографики его теряют.

Исправление: спрашивать о `!Unpin` или явно противопоставить два типа;
заменить демонстрацию и поправить изображение.

[Урок](https://crabrix.com/learn/concurrency/pinning-intuition/) ·
[Документация Pin](https://doc.rust-lang.org/std/pin/struct.Pin.html#pinning-a-value-of-a-type-that-implements-unpin)

### 7. P2 — Error Handling: panic ошибочно приравнен к обязательному завершению процесса

Правильным помечен ответ **Ends the process, removing any chance to recover**
для `unwrap()`. В обычной конфигурации unwinding панику можно перехватить;
процесс в контрпримере продолжает работу. При `panic=abort` поведение другое.
Платформенная конфигурация iPhone/WASI не делает абсолютное утверждение
правильным для общего урока Rust.

Исправление: ответ «паника при Err; unwinding/abort зависит от конфигурации».
Сохранить рекомендацию возвращать Result для ожидаемых ошибок; catch_unwind
не предлагать как замену нормальной обработке Result.

[Урок](https://crabrix.com/learn/projects/errors/) ·
[Документация catch_unwind](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html)

### 8. P2 — cfg/features: отключённый код всё ещё должен разбираться синтаксически

Правило: **a disabled branch never has to be valid**. Это слишком широко.
`#[cfg(any())] fn disabled() { let = ; }` отклоняется парсером, хотя условие
всегда ложно. Можно исключить неподходящий тип или недоступный платформенный
API из проверки типов, но нельзя обещать произвольный неверный синтаксис.

Исправление: разграничить синтаксический разбор и name/type checking.

[Урок](https://crabrix.com/learn/systems/cfg-features/) ·
[Rust Reference](https://doc.rust-lang.org/reference/conditional-compilation.html)

### 9. P2 — cfg/features: default-features=false не запрещает std во всём графе

Ответ обещает **so std is not enabled**, обратная связь — точный выбор
только желаемых features. Объяснение ниже правильно упоминает объединение
features, что противоречит абсолютному ответу.

Контрпример из трёх локальных crates собирается **offline**: приложение
запрашивает зависимость с `default-features=false`, другая обычная
зависимость включает её defaults, и `cfg!(feature="std")` остаётся true.

Исправление: «эта декларация не запрашивает default features; другой путь
зависимостей может их включить».

[Cargo Book: feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification)

### 10. P2 — Async Cancellation: неоднозначный вопрос с одним допустимым ответом

На вопрос **When may cancellation occur?** принимается только
**At an await suspension**, а **Before async fn starts** считается неверным.
При этом созданный future можно удалить до первого poll и до начала
исполнения тела. Контрпример показывает, что тело не было выполнено.

Исправление: уточнить вопрос про уже исполняющуюся задачу и кооперативную
отмену между poll, либо разрешить несколько корректных ответов. Различать
создание future, начало исполнения тела и приостановку на await.

[Урок](https://crabrix.com/learn/concurrency/async-cancellation/) ·
[Future: runtime characteristics](https://doc.rust-lang.org/std/future/trait.Future.html#runtime-characteristics)

### 11. P2 — Composite Indexes: абсолютное правило противоречит современным СУБД

Правило **leftmost prefix ... nothing else** и ответ «индекс не используется
без фильтра tenant_id» не универсальны. PostgreSQL документирует B-tree
skip scan и возможность использования ограничений по более поздним столбцам.
В этом же уроке более поздний абзац уже правильно оговаривает вариативность
планировщиков, но вопрос её игнорирует.

Исправление: указать СУБД/тип индекса, объяснить эффективность ведущих
столбцов и требовать EXPLAIN с данными вместо безусловного «No».

[Урок](https://crabrix.com/learn/interview/q-indexes/) ·
[PostgreSQL: multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html)

### 12. P2 — Complexity: подпись говорит, что O(n) и O(log n) — один класс

В примере линейный поиск помечен O(n), поиск по дереву — O(log n), а подпись
гласит **Same complexity class, very different constants**. Это разные
асимптотические скорости роста. Обсуждение констант не делает их одинаковыми.

Исправление: явно указать разные порядки роста, затем объяснить роль
констант и локальности на конкретных размерах данных.

[Урок](https://crabrix.com/learn/interview/q-complexity/)

## Системные пробелы наполнения и проверки

### A. На 200 алгоритмов — 20 повторяющихся Rust sketches

В каждом семействе десять алгоритмов используют один и тот же фрагмент.
Особенно заметные несоответствия:

- Fenwick Tree и Segment Tree показывают функцию построения prefix sums.
- Monotonic Stack и Largest Histogram показывают проверку скобок.
- Bellman–Ford и Dinic Max Flow показывают только комментарий про Dijkstra.
- Median of Medians и Quicksort показывают insertion sort.
- Sparse Table и Suffix Automaton показывают общий комментарий без реализации.

Текст оговаривает, что sketch может быть связанным примером. Это не делает
его объяснением инварианта конкретного алгоритма. Следует дать каждому
паттерну свой минимальный пример, состояние и реальный пошаговый разбор.
Все группы сохранены в `atlas.sketchGroups`.

### B. 600 шагов Atlas используют только три вопроса-шаблона

По 200 повторений вопросов про инвариант, use cases и performance target.
Во всех 600 `Trace a transition` содержит инструкцию **Apply one legal
update**, а не выполненный переход состояния с конкретными числами.
Это не 600 самостоятельных разборов. Вопросы и трассировки надо писать под
алгоритм: предсказать следующий шаг, найти нарушенный инвариант, выбрать
контрпример, объяснить границу или оценить конкретный фрагмент кода.

### C. Четыре запуска harness — только два различных входа

У всех 200 challenges четыре вызова, но после разрешённого `trim()` остаётся
только **два различных входа**: видимый и один скрытый. Два остальных
проверяют пробелы вокруг тех же строк. Это полезная проверка парсинга,
но недостаточное основание утверждать, что алгоритм проверен на широком
наборе границ. Нет проверки заявленной асимптотики; она остаётся учебной
целью, а не фактом, доказанным harness.

Нужны независимые boundary/adversarial cases по контракту конкретного
алгоритма и проверка допустимости результата там, где ответ не уникален.

### D. Инфографика диапазонов смешивает разные соглашения об endpoints

У Imos задача явно задаёт включительные `[L,R]`, но панель Sweep Events
предлагает **remove at R**. Для дискретного включительного диапазона
разность нужно вычитать в **R+1**. Такая схема может быть корректна для
полуоткрытых интервалов, но соглашение на рисунке не указано, а подпись
урока предлагает применять панель к его примеру. Исправить соглашение и
синхронизировать рисунок с задачей.

### E. Вторичные редакторские замечания

- PhantomData: «Usually zero» заменить гарантией размера самого
  `PhantomData<T>` — 0, alignment — 1 для всех T. Не смешивать это с
  рассуждением о полном layout содержащей структуры.
  [Документация layout](https://doc.rust-lang.org/std/marker/struct.PhantomData.html#layout).
- Сайт подписывает все примеры **Read the Rust** и использует только
  Rust tokenizer (`site/components/SyntaxCode.tsx`). Среди блоков есть TOML,
  SQL и смешанные многофайловые фрагменты. Нужны язык и путь файла на уровне
  блока; иначе часть подсветки и подписи не соответствует содержимому.

## Воспроизведение

```sh
python3 docs/audits/academy-2026-10-27/audit.py --courses ../crabrix-courses
python3 docs/audits/academy-2026-10-27/check_public_pack.py
```

Первый скрипт использует стандартную библиотеку Python, rustc и cargo,
записывает временные программы в `build/academy-audit-20261027`.
Второму нужны сеть и Python `certifi`; он скачивает публичный архив по URL
из каталога с ограничением размера и проверкой SHA-256. Он не является
новым тестом Ed25519-подписи.

Этот проход создаёт отчёт и воспроизводимые доказательства. Исправления
учебного контента и публикация новых пакетов в него не входят.
