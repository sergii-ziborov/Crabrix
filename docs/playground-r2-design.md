# Playground R2: проект устойчивой идентичности файлов

Статус: утверждён владельцем 2 ноября 2026 вместе с тремя предложенными решениями, реализация идёт по шагам раздела «Порядок выпуска». Покрывает FS-03, FS-04, MCP-03 и R2-часть CORE-01 из задания на обновление Playground. Сверено с `main` `e433e11` и SDK `408e416`, прошёл независимую проверку по коду, её замечания учтены.

## Коротко

- Текст файла адресуется постоянным `fileId`, а путь становится изменяемым полем. Правка, задержанная на время переименования, попадает в тот же файл.
- Удаление ставит отметку и не трогает текст. Правка, пришедшая после удаления, остаётся в списке восстановления.
- Чтение проекта никогда не падает из-за конкурентных правок. Коллизии и превышения лимитов показываются как состояние проекта и блокируют только запуск.
- Выпущенные клиенты в комнату нового формата не войдут: их не пустит релей, а если всё же получат данные, откажут сами, ничего не записав.
- Существующие комнаты не мигрируют. Они живут не больше 24 часов и остаются на v1 с нынешним ограничением.

### Найденные ошибки в текущем v1

Обе есть в живых комнатах, и ограничение R0 их не закрывает, потому что создавать файлы в общей комнате разрешено. Проверено на уровне документа, без релея.

1. **Комната становится нечитаемой.** Если двое одновременно создают `helper.rs` и `Helper.rs`, объединённый документ не проходит проверку. `receive` и `receiveState` вызывают один и тот же `documentFromY`, поэтому по коду все участники остаются в цикле переподключения. Так же должно сработать превышение лимита 16 файлов двумя одновременными созданиями.
2. **Текст исчезает молча.** Если двое одновременно создают один и тот же путь, остаётся только один текст.

Отдельно v1 чинить не предлагаю: старые клиенты всё равно останутся с этими ошибками, а v2 снимает обе.

## Модель документа

Внутри Yjs:

```text
meta      Y.Map   schemaVersion: 2, name, edition, origin?, entryFileId
entries   Y.Map   fileId -> Y.Map { path, deleted?, digest?, purged? }
t:<fileId> Y.Text  текст файла, отдельный корневой тип
ops       Y.Map   operationId -> { hash, at }
```

- `fileId`: 128 случайных бит, 22 символа base64url. Ключи другого вида читатель игнорирует.
- Текст лежит в корневом типе, потому что корневой тип нельзя удалить. Код v2 никогда не вызывает `entries.delete`.
- Формат фиксируется один раз: `schemaVersion` пишется только при создании, а читатель выбирается по кодеку комнаты с релея. Поздняя запись в `meta` формат не меняет. Иначе одна ошибочная запись `3` сделала бы комнату нечитаемой для всех.
- `path`, `deleted`, `entryFileId`, `name`, `edition`: поля «последняя запись побеждает». Порядок задаёт Yjs, он одинаков у всех клиентов.
- `digest`: некриптографический отпечаток текста, каким его видел удаляющий. Участники комнаты и так держат ключ, поэтому защита от подделки здесь не нужна. Коллизия отпечатка только уберёт пометку конфликта, строка останется в восстановлении.

Снаружи формат прежний: `PlaygroundDocument` со `schemaVersion: 1` и картой `path -> text`. Компилятор и `crabrix-runtime-source-v1` не меняются. В Y.Doc стоит `schemaVersion: 2`, в проекции `1`: это разные версии, версию документа знает только codec.

## Проекция

Новая функция `readProject(doc)` никогда не бросает исключение на семантически возможном состоянии:

```ts
type ProjectState = {
  name; edition; origin?;                        // неверные значения заменяются на "playground" и 2024
  files: { id; path; requestedPath; text }[];   // path всегда уникален и допустим
  recovery: { id; path; text; bytes; conflict: boolean; orphan: boolean }[];
  entryId: string | null; entryFallback: boolean;
  blocked: ("no-files" | "no-entry" | "files" | "file-bytes" | "source-bytes" | "text")[];
  records: number;                               // все записи entries, для лимита 64
};
```

Строка восстановления это удалённый файл с непустым текстом. Отметку `purged` ставит очистка, чтобы клиенты сбросили Undo этого файла, проекция на неё не смотрит. Причина `text` блокирует запуск, если в файл попал NUL или недопустимый UTF-16.

`documentFromY(doc)` остаётся строгим: читает `readProject`, проверяет `validatePlaygroundDocument` и бросает ошибку, если `blocked` не пуст. Его используют только запуск и API с исполняемым результатом. Экспорт читает `readProject`, поэтому работает и в заблокированной комнате, и после её истечения. В ZIP попадают живые файлы и, если есть, строки восстановления в отдельной папке `crabrix-recovery/`. «Copy to local» в заблокированной комнате недоступна, вместо неё предлагается экспорт.

Детерминированные правила, по `fileId` в порядке кодовых единиц:

| Ситуация | Результат |
|---|---|
| Запрошенный путь занят, совпадает с каталогом или расходится в написании каталога | Выигрывает меньший `fileId`, проигравший получает `conflict-<id8>-<имя>` в корне и пометку в дереве |
| Такое имя не проходит проверку (`LICENSE`, `NOTICE`, путь длиннее лимита), или путь недопустим сам по себе | `recovered-<id8>.txt`, при занятом имени берётся полный ID |
| Запись `entries` неверного типа | Как отсутствующая запись, чтение не падает |
| Непустой `t:<id>` без годной записи в `entries` | Строка восстановления с `orphan: true` |
| `entryFileId` указывает на удалённый файл | Первый живой `.rs` по пути и `entryFallback: true` |
| Нет `.rs` или нет живых файлов | `blocked`, запуск отключён, редактирование и восстановление доступны |
| Превышены 16 файлов, 64 или 128 КиБ | `blocked`, разрешены только уменьшающие действия |

Сохранённый `path` при коллизии не меняется. Чтение ничего не записывает, иначе клиенты начнут спорить записями. Конфликт разрешает человек обычным переименованием.

Входящее обновление после входа в комнату больше не отклоняется по содержимому. Иначе одинаковый отказ у всех участников снова сделает комнату нечитаемой. `schemaVersion` проверяется один раз при входе, и несовпадение с кодеком комнаты открывает комнату только на чтение и экспорт.

Пустой корневой текст строкой восстановления не считается. Курсор присутствия с неизвестным `t:<id>` создаёт на одном клиенте пустой корень, который исчезает после снимка, и клиенты не должны расходиться из-за него.

## Операции

Единый модуль планирования используют web, native и SDK:

| Операция | Изменение |
|---|---|
| `create`, `copy` | Новый `fileId`, у копии история начинается заново |
| `write` | Минимальная правка `t:<id>` |
| `move`, `moveFolder` | Только `path`, одним обновлением |
| `delete`, `deleteFolder` | `deleted: true` и `digest`, текст остаётся |
| `restore` | `deleted: false`, при занятом пути план спрашивает новый |
| `purge` | Явное действие: `purged: true`, текст очищается |
| `setEntry`, `setEdition`, `setName` | Поля `meta` |

План считается целиком до записи и содержит ревизию, затронутые ID, старые и новые пути, коллизии, бюджеты, итоговый entry, удаляемые файлы и изменения локального состояния. Одна ошибка отменяет весь план (T20). Для перемещённых `.rs` план только предлагает Check: ссылки `mod`, `#[path]`, `include_str!` не переписываются.

Старый `crabrix_apply_changes` становится адаптером: совпавший путь это `write`, новый путь это `create`, `text: null` это `delete`. На v2-документе `updateYDocument` бросает ошибку, чтобы обойти эти правила было нельзя.

Импорт порождает операции только для путей, которые пользователь выбрал в плане. Перед применением он сравнивает ревизию плана с текущей (раздел 5.6 задания) и при расхождении просит пересчитать план. Файл, созданный другим участником, пока открыт диалог, импорт не затронет.

Приложение сейчас отправляет любое изменение проекта целым документом через `connection.replace` (`CompilerViewModel.swift:3048`), поэтому мост переводит `replace` в операции по базовой карте `path -> fileId`, которую Swift подтвердил последней:

- тот же путь это `write` в прежний ID, даже если файл уже переименован другим участником;
- исчезнувший путь и новый путь с тем же текстом это `move` того же ID;
- остальные исчезнувшие пути это `delete`, остальные новые пути это `create`.

### Два режима применения

- **Человек в интерфейсе.** Обновление уходит обычным потоком, без сравнения ревизии, работает и офлайн. Стабильные ID делают переименование независимым от правок текста, а сравнение ревизии отклоняло бы его при каждом чужом нажатии клавиши.
- **Агент через MCP.** План опирается на прочитанную ревизию, поэтому `crabrix_apply_operations` требует `expectedRevision` и generation. Устаревший план отклоняется (T16).

Здесь проект уточняет T16: в интерфейсе устаревшее переименование не отклоняется, а применяется к тому же файлу, текст B сохранён. Цель T16 достигается, но другим путём, поэтому это вынесено в решения владельца.

### MCP

Новые инструменты: `crabrix_plan_changes` и `crabrix_apply_operations`, до 32 операций за вызов. Окончательные имена закрепляются в API review SDK. План возвращает `planHash`, применение проверяет его заново вместе с правами и ревизией.

Повтор операции (T22) защищён записью в самом документе, потому что релей не видит содержимое. Применение записывает `ops[operationId] = { hash, at }` в той же транзакции. При повторе клиент читает состояние: тот же hash даёт `alreadyApplied` без мутации, другой hash даёт ошибку. Хранятся 64 записи, самая старая вытесняется. После вытеснения от второй мутации защищает `expectedRevision`.

До R3 у комнаты один edit-доступ, поэтому привязка к principal сводится к комнате. Отдельные principal добавит R3.

В `revision()` для v2 добавляются ID файлов и строки восстановления, чтобы правки структуры при том же тексте меняли ревизию.

## Удаление и лимиты

| Лимит v2 | Значение |
|---|---|
| Живые файлы | 16 файлов, 64 КиБ на файл, 128 КиБ всего, как сейчас |
| Строки восстановления | 16 |
| Текст в восстановлении | 96 КиБ |
| Все записи `entries`, включая очищенные | 64 |
| Записи `ops` | 64 |
| Снимок комнаты | 512 КиБ вместо 256 |

- Удаление, которое не помещается в бюджет восстановления, отклоняется до записи. Варианты: очистить старые строки, скачать их или перейти в новую комнату. Поздняя чужая правка бюджет не отклоняет, она только запрещает следующие удаления.
- Строка восстановления хранится до явной очистки или конца комнаты. Перед концом комнаты предупреждение называет число таких строк.
- Правка после очистки снова выводит файл в восстановление как конфликт.
- Очистка сбрасывает `UndoManager` этого файла у каждого клиента, получившего `purged`, иначе Undo вернёт очищенный текст.
- Снимок всегда кодируется через копию в новом `Y.Doc`. `UndoManager` удерживает удалённое содержимое, и без копии снимок вырастает на сотни КиБ, а очищенный текст остаётся в его байтах.
- Лимит снимка поднимается только для v2. Измерение показало, что при 128 КиБ и сильной фрагментации 256 КиБ не хватает уже в v1. Общие лимиты памяти релея и лимит состояния 2 000 000 символов не меняются. 10 000 пар правок не поместятся и в 512 КиБ: на этот случай остаётся нынешний путь с явным сообщением и загрузкой копии.
- Чтобы 512 КиБ были достижимы, маршрут `rooms/[id]` выбирает предел тела по кодеку уже проверенной комнаты (720 000 символов для v2), а мост приложения получает снимок и события в base64 вместо массива байт. `PlaygroundCodec.call` тогда укладывается в свои 2 000 000 символов для любой комнаты в пределах `roomBytes`.
- «Copy to local» и новая комната берут живые файлы. Строки восстановления в них не переносятся, поэтому диалог показывает их число и предлагает скачать.
- Фильтр размера в редакторе разрешает правку, которая уменьшает текст, иначе в заблокированном файле нельзя удалить лишнее.
- Отдельные сущности пустых папок в R2 не входят: проблему идентичности они не решают, а формат усложняют.

## Клиентское состояние

- Интерфейс работает через ключ файла: в v1 это путь, в v2 `fileId`. Реестр редактора, выбранный файл и точки останова привязаны к ключу, поэтому переименование ничего не надо пересчитывать (T24). Отладчик работает с путями и во время запуска, поэтому точки останова переводятся в пути при каждом изменении карты, а место остановки обратно в ключ.
- Набор в редакторе идёт с origin привязки `y-codemirror`. Операции используют свои origin `import`, `structure`, `mcp`, никогда `null`, и `UndoManager` их не отслеживает.
- Присутствие разрешает курсор только для `t:<id>`, который есть в `entries`. Неизвестное имя отбрасывается до `createAbsolutePositionFromRelativePosition`, потому что этот вызов создаёт корневой тип.
- Локальный документ до шага 7 остаётся v1. Публикация в v2 создаёт новый `Y.Doc` из проекции, и реестр редактора начинается заново. После шага 7 локальные документы сразу v2, и реестр сохраняется.
- Мост приложения снимает исходящие обновления последним шагом ответа, чтобы ошибка чтения не потеряла их, как сейчас может случиться в `playground-bridge.ts:63-67`.
- Когда `blocked` не пуст, мост не возвращает `document`, а возвращает `blocked` и число строк восстановления. Иначе `PlaygroundDocument.validated()` бросит ошибку и приложение уйдёт в цикл переподключения. Приложение переводит редактор в режим чтения и показывает уведомление.

## Совместимость

Вход в комнату проверяется в двух независимых местах.

1. **Релей.** `POST /rooms` принимает `codec: 2`. Новые клиенты присылают `codecs=1,2` в запросе потока и заголовком в остальных запросах. Если комната v2, а клиент формат не объявил, релей отвечает 426 с текстом «обновите Crabrix», не занимает слот участника и не отдаёт зашифрованное состояние. Проверка стоит до лимита частоты, чтобы сообщение не сменилось на 429.
2. **Клиент.** Даже получив данные, выпущенный клиент откажет сам, что подтверждено опытом для всех трёх.

| Клиент | Что увидит при входе в v2 |
|---|---|
| Открытая старая вкладка web | Текст релея в статусе, повтор раз в 2 секунды |
| Приложение до v2 | «The interview connection is unavailable.» и повтор: текст релея оно не читает (`PlaygroundLiveSession.swift:194`), просьбы обновиться не будет |
| SDK 0.3.5 | `JOIN_TIMEOUT` через 15 секунд: такой SDK не распознаёт новый статус |
| Более ранние SDK 0.3.x (читались 0.3.0 и 0.3.3) | Такой же таймаут, без машинного кода ошибки |
| Новый клиент в комнате v1 | Обычная работа с нынешним ограничением R0 |
| Новый клиент в комнате будущего формата | Тот же отказ, механизм расширяется без изменений |

Старое приложение объяснить причину не сможет, поэтому диалог Share в web и кнопка Open in Crabrix для комнаты v2 заранее предупреждают: «нужен Crabrix 1.1.5 или новее».

Код v1 остаётся надолго: старые SDK и приложения продолжат создавать комнаты v1.

Каждый шаг выпускается отдельно и ничего не обещает публично до шага 7.

1. **Codec и тесты.** `readProject`, операции, планировщик. Подключения к интерфейсу нет. Выполнен: `site/lib/playground-codec-v2.ts` и `site/tests/playground-codec-v2.test.mjs`, включая адаптеры `crabrix_apply_changes` и `replace` приложения.
2. **Релей.** Поле `codec`, проверка входа, лимит снимка для v2. Регрессия v1.
3. **Web-клиент.** Сессия и присутствие читают обе версии. Комнату v2 можно создать только за внутренним флагом.
4. **Web-интерфейс.** Дерево, диалоги, панель восстановления, реестр по ключу. Импорт как план операций.
5. **SDK 0.4.0.** Перенос core с зафиксированным происхождением, новые инструменты, сборка Rust и Go, skill. Проверка против боевого релея.
6. **Приложение 1.1.5.** Новый бандл, правка и выделение по `fileId`, следование за чужим переименованием. Подача на ревью только по слову владельца.
7. **Новые комнаты на v2 по умолчанию.** Описание на сайте и `/ai/`. Ограничение R0 снимается только для v2.

## Решения владельца

Все три приняты 2 ноября 2026 в предложенном виде.

1. **Когда включать v2 по умолчанию.** Предлагаю через две недели после выхода 1.1.5 в App Store. Цена раннего включения: пользователь старой версии приложения не откроет комнату, созданную в web, и увидит только «The interview connection is unavailable».
2. **Объём приложения в 1.1.5.** Предлагаю без новых панелей: его файловые действия идут через тот же `replace`, а мост переводит их в операции. Приложение следует за чужими переименованиями и показывает «N файлов можно восстановить в браузере», а в заблокированной комнате переходит в режим чтения. Тексты при этом не теряются. Раскладка экранов не меняется, но новые состояния нужно посмотреть на Duo и iPad.
3. **Уточнение T16.** Предлагаю отклонять устаревшую операцию только в MCP, а в интерфейсе применять её к тому же файлу с сохранением чужого текста. Буквальное выполнение T16 в интерфейсе отклоняло бы переименование при каждом чужом нажатии клавиши.

## Инварианты для проверки

Проверяются тестами и случайной конкуренцией на нескольких клиентах с произвольным порядком доставки:

1. Клиенты, получившие одни и те же обновления, дают побайтно одинаковый `readProject`.
2. Подтверждённая правка всегда доступна: в живом файле или в восстановлении, пока её явно не очистили.
3. `readProject` не бросает исключение на любом обновлении, которое принял Yjs, включая неверные типы и поздние записи в `meta`.
4. В `files` пути уникальны и проходят полную проверку пути из `validatePlaygroundDocument`.
5. Переименование не меняет `fileId`, текст и Undo.
6. Снимок и повторное чтение дают тот же `readProject` и те же ID, а курсоры присутствия на результат не влияют.
7. Выпущенный клиент не получает состояние v2 от релея и не создаёт исходящих обновлений, если получит его иначе.
8. Отклонённый план не меняет документ. Повтор применённой операции не создаёт вторую мутацию.

| Сценарий задания | Как закрывается |
|---|---|
| T16 | MCP: `expectedRevision` отклоняет. Интерфейс: применяется к тому же ID, текст сохранён |
| T17, T18 | Текст адресуется ID, старый путь не воскресает, в том числе при входе после офлайна |
| T19 | v1 сохраняет нынешнее ограничение |
| T20 | План целиком и одно обновление, коллизия отменяет всё |
| T21 | Строка восстановления с `conflict: true` |
| T22 | `ops`, `alreadyApplied`, отказ при другом hash |
| T23 | Отказ релея и отказ клиента |
| T24 | Ключ файла вместо пути в реестре и точках останова |

Фикстуры прогоняются на TypeScript-исходниках, на собранном бандле SDK и на упакованном `PlaygroundCodec.js` в JavaScriptCore. Реализация CRDT остаётся одна.
