# Runtime integration

The public [CrabrixRuntime fork](https://github.com/sergii-ziborov/crabrix-runtime) keeps WasmKit upstream history and notices. Its base is WasmKit 0.4.1 at `a0471eaee817c523b8023d8ebb1c70ff70b7950a`; this development app pins fork commit `d996f0d11dff54734b5670d58062e22c6e01f949`. There is no second production engine in the SwiftPM graph. The old vendored source remains only as historical source in the repository and is not linked into the app target.

`RustcRuntime` uses token threading, software memory bounds checks, upstream fuel metering, the fork's cancellation probe sampled once per 64 fuel checkpoints (including the first charge), and a fresh `Store` and WASI instance for each invocation. Host calls and bulk memory/table operations check directly; network socket imports return guest `ENOSYS`. Separate `CompilerHostPolicy` and user program policy set memory, table, fuel, wall-clock, and output budgets. A fuel trap maps to a typed instruction-budget stop. The compiler and program each receive a write-time WASI stdout/stderr budget (16 MiB and 1 MiB respectively). The program's writable sandbox also has a quota monitor.

The fork can reserve a virtual address range for software-checked linear memory, then commit pages in place on `memory.grow`. The app caches separate engines with a 2 GiB reservation hint for rustc and a 64 MiB hint for user programs. These are virtual ranges, not committed RAM allowances. The existing resource limiter still decides every grow; allocation falls back to the old malloc path if reservation fails or an allowed grow exceeds it. On optimized arm64, an out-of-bounds load in direct dispatch returned zero with software bounds; the fork now selects token dispatch for every software-bounds engine, including a direct request. The [earlier five-run Release Simulator report](performance/2026-09-30-reserved-memory-safety-simulator.json) measured a 2.02× changed-Check median improvement at the preceding `fbe46d9` fork against its own baseline with the same old compiler artifact. The [new A/B/A heavy-CLI report](performance/2026-10-02-sampled-cancellation-heavy-cli-simulator.json) measured 1.61–1.63× for one dependency-rich project on the sampled fork versus `fbe46d9`, using the same own compiler candidate. Physical-device speed and memory pressure remain unmeasured.

The fork adapter tests cover fuel exhaustion, pure-loop cancellation, fresh-run recovery, memory page limits, guarded WASI links, read-only nested descriptors, and the shared output budget. Its full Swift suite passed 464 tests across 15 targets after the sampled-probe change, including token/direct cancellation-bound coverage. The new revision passed five selected old-compiler and five own-compiler Release Simulator fuel/Stop/deadline app gates. The preceding `fbe46d9` revision passed nine selected compiler/sandbox gates, including E0502, guided Check corpus, compile Stop, a user-program memory limit, and a unique-source Run. A separate iOS Simulator OOB gate verified that a direct request under software bounds selects token dispatch and traps beyond committed memory. Some Run gates used warm disk artifacts, so their pass is not counted as a fresh compiler execution. See [validation](VALIDATION.md) for earlier gates.

## Remaining gates

Compiler source, sysroot, and registry preopens use read-only WASI rights; `/work` and `/tmp` remain writable outputs. Check cache hits retain their full diagnostics and spans, with a bounded in-memory snapshot cache; the [simulator comparison](performance/2026-09-30-warning-check-simulator.json) records this fix and the limited speed evidence. `RustcRuntime` parses bundled and cached modules through WasmKit's file reader, avoiding a full `Data` to `[UInt8]` conversion; [the five-run parser/dispatch probe](performance/2026-09-30-file-parser-dispatch-simulator.json) records unchanged Check correctness and limited speed observations. Parsed student-program modules now have an eight-entry LRU with a 64 MiB admission budget based on four times the Wasm file size; memory warnings queue eviction after the active compile. This is a cost proxy, not an RSS guarantee. Persisting program artifacts copies the file without loading it into a second whole-file `Data` buffer. The separately cached bundled compiler module remains available after program-cache eviction. Direct dispatch remains disabled pending the full Run/Cargo/device gates. Cold host parse cannot currently be stopped in the middle of parsing. Compiler workspace/tmp disk quotas, device measurements, and physical memory-pressure recovery still need evidence. Do not interpret the existing fuel tests as proof of these separate properties.
