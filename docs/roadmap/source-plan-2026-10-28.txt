1. Цель и границы

Сделать Crabrix удобной средой для полного рабочего цикла: открыть или создать проект, изменить программу, проверить её тестами, сохранить осмысленную версию, перенести работу на другое устройство и продолжить ту же историю разработки.

Ближайший приоритет — сохранность проектов, сохранение смысла программы в Debug, корректные операции Build / Run / Test / Format и Git. Затем — семантические возможности редактора, офлайн-визуализации Academy, завершение TypeScript-проверки и понятная совместимость проектов. C и C++ включены в дальнейший план с отдельными этапами технического подтверждения и определения поддерживаемого профиля.

2.3. Что действительно стало лучше после прошлого разбора

Связность продукта. Последние изменения устраняют ситуацию, когда встроенный Rust + Web generator работает через Run, но отказывается запускаться через Debug из-за include_str! / include_bytes!. Теперь instrumenter получает ресурсы проекта; обычные HTML/CSS/JS-данные сохраняются, а включаемый как данные Rust-исходник берётся из отдельной неизменённой копии. Есть ограничения объёма, обработка коллизий имён, относительных путей и сохранение координат строк. Это решение реальной несовместимости двух соседних действий пользователя. Исправления ресурсов, instrumenter.

Работа на маленьком экране. Убран прозрачный слой шириной 28 points, перехватывавший нажатия на breakpoint gutter до начала Debug. Существующий родительский жест открытия Files оставлен. По отчёту повторный UI-сценарий проверяет одиночный tap, Continue, Step и работу JavaScript в сгенерированной странице на iPhone/iPad Simulators. Отчёт.

Качество доказательств. В репозитории записаны восемь native host tests с настоящим offline compiler, 23 сравнения нормального и Debug-выполнения в browser compiler, два явных отказа для неподдерживаемых форм, 34 site tests, type checking и production build. В отчёте сохранено различие между Simulator и физическим устройством, а публичный браузерный сценарий повторён с отключённой после получения toolchain сетью. Это сильнее проверки наличия кнопки или отдельного mock. Данные приведены из отчёта автора; весь этот набор в данном разборе повторно не запускался. Машиночитаемый отчёт.

Документация частично приведена в порядок. README уже описывает build 110; Technology явно отделяет поставляемый compiler от кандидатов и ограниченные build scripts от неподдерживаемых host-возможностей. 2.4. Моя оценка Crabrix

Crabrix уже имеет убедительное собственное назначение: изучать Rust и системное программирование через настоящую локальную компиляцию, наблюдение за выполнением и собственные проекты. Наиболее ценное сочетание — Academy, проверенные алгоритмические примеры, исходный debugger, подготовка зависимостей для офлайн-работы и возможность продолжить эксперимент в приложении. Эти части усиливают друг друга.

Особенно удачна разница между двумя способами объяснения программы. Atlas воспроизводит заранее проверенный пример, связанный с хэшем исходника; Debug работает с текущей пользовательской программой в поддерживаемых границах. Пользователь может сначала понять образец, затем изменить его и исследовать последствия. Полезно сделать этот переход главным сценарием продукта. Визуализации, debugger, Guide.

Сильная инженерная сторона — локальная модель исполнения, контроль ресурсов, конкретная идентичность compiler/runtime, атомарные снимки проектов и отчёты с ограничениями проверок. Добавление ресурсоёмких возможностей уже сопровождается попыткой измерять и ограничивать их. Новые исправления Debug продолжают этот подход.

Главный недостаток сейчас — незавершённость повседневного жизненного цикла проекта. Уже можно получить сложный результат, но ещё нельзя рассчитывать на полный привычный цикл пользовательских тестов, форматирования, истории Git и семантического редактирования. Дополнительно найдены конкретные риски сохранения и ошибки инструментирования. Следующая большая прибавка ценности, по моей оценке, придёт от завершения этих действий.

Оценка коммерческого результата пока ограничена: исходники и сайт показывают реализацию, но не показывают удержание, частоту возвращения, готовность платить или то, как новые пользователи справляются без автора. Поэтому в документе нет выдуманного рейтинга качества, сроков окупаемости или обещанного процента роста.

2.6. Что из старого плана ещё не закрыто

Повторно проверенные ProjectLibrary, LocalProjectLoader, CrabrixProjectDocument, GitHubProjectImporter, ProjectTerminalSession и RustCodeCompletion имеют те же Git blob SHA, что и на предыдущей базе. Поэтому скрытые файлы, несогласованные лимиты ZIP, build → onRun, отсутствие проектного cargo test и полноценного Git не следует считать исправленными обновлением отладчика. При этом автосохранение, аварийный снимок, существующее шаблонное дополнение, Academy-проверки, исходный debugger и веб-визуализации уже есть. План расширяет их и исправляет границы; он не предлагает создавать их заново.

3. Принципы реализации

Сохранность важнее расширения форматов. Допустимые файлы и история проекта не должны теряться при открытии, сохранении, импорте, checkout или обновлении приложения.

Каждая операция относится к конкретной версии исходников. Старый результат не может заменить новые изменения пользователя.

Существующие сценарии сохраняются. Расширения не должны ломать Academy, Cargo, Web Preview, отладчик, Playground, темы или устойчивую геометрию редактора.

Отладчик сохраняет смысл программы. Вставленные checkpoints не меняют владение, разрешение имён и данные ресурса; неподдерживаемый случай получает объяснимую границу.

Границы поддержки видимы. Успешная проверка синтаксиса, проверка типов, сборка и выполнение имеют разные значения.

Офлайн-работа остаётся полноценной. Локальные проекты, коммиты и подготовленные зависимости не требуют аккаунта или скрытых сетевых запросов.

Полная Academy сохраняется. Новые лаборатории и инструменты дополняют существующие курсы.

Ограничения проверяются согласованно. Количество Cargo-пакетов, исходных файлов, записей ZIP, байтов репозитория и ресурсов выполнения — отдельные величины.

Публикация не следует автоматически из наличия кода. Для выпуска нужны результаты проверки соответствующего артефакта и подтверждённый статус доставки.

5. P0 — сохранность и корректность операций

P0-01. Скрытые файлы

Подтверждено исходниками. ProjectStore записывает все элементы project.files, а чтение использует .skipsHiddenFiles. LocalProjectLoader также пропускает скрытые файлы; при этом его whitelist содержит .gitignore и .rustfmt.toml. ProjectLibrary, LocalProjectLoader.

Ожидаемый дефект. Скрытый файл или содержимое скрытого каталога могут отсутствовать после повторного чтения допустимого сохранённого проекта.

Работа:

Разделить правила хранения, отображения, редактирования и компиляции.

Сохранять допустимые скрытые исходники и конфигурацию.

Исключать служебные каталоги по явному правилу, а не по наличию точки в имени.

Управлять будущим Git-хранилищем отдельно от пользовательских исходников.

Сохранить проверки безопасных путей и текущий механизм атомарной записи.

Проверить миграцию существующих сохранений; не считать восстановленными файлы, отсутствующие и в текущем, и в резервном снимке.

Приёмка:

Проект с src/main.rs, .gitignore, .rustfmt.toml, .cargo/config.toml и вложенным скрытым каталогом сохраняет одинаковые пути и содержимое после перезапуска.

Импорт через Files и экспорт/повторный импорт сохраняют тот же набор допустимых файлов.

Метаданные Crabrix не начинают ошибочно восприниматься как пользовательские исходники.

Прерывание сохранения не повреждает единственную рабочую копию.

Существующие подготовленные browser-зависимости и курс-проекты продолжают открываться.

P0-02. Ограничения и обратимость экспорта

Подтверждено исходниками. LocalProjectLoader допускает 2 048 файлов, тогда как CrabrixProjectArchive ограничивает ZIP 1 024 записями. Экспорт записывает проект без соответствующей проверки числа ZIP-записей. LocalProjectLoader, CrabrixProjectDocument.

Ожидаемый дефект. Допустимый проект с 1 200 небольшими файлами может экспортироваться, но не пройти собственный ZIP-импорт. Каталоги и метаданные дополнительно расходуют лимит записей.

Работа:

Определить одну согласованную политику поддерживаемого проекта и форматов переноса.

Отдельно учитывать исходные файлы, каталоговую структуру, метаданные, сжатый и распакованный размер.

Проверять экспортируемый результат на совместимость с собственным импортом.

Сохранять ограничения ресурсов и защиту от небезопасных путей.

Объяснять отказ конкретным превышенным пределом.

Не смешивать этот вопрос с текущим потолком 2 048 уникальных Cargo-пакетов.

Приёмка:

Проект на поддерживаемой границе количества файлов экспортируется и импортируется обратно.

Проверены 1 200 малых файлов, глубокие каталоги и дополнительная метаинформация.

Пути, тексты и идентичность проекта сохраняются согласно документированному формату.

Отказ происходит до повреждения или частичной замены существующего проекта.

Повторное открытие после экспорта и после отменённого импорта не меняет исходный проект.

P0-03. Согласование операций по версии исходников

В проекте уже есть WorkspaceRevision с идентичностью исходного дерева и инструментов. Его нужно использовать как основу и проверить полноту применения. WorkspaceRevision.

Работа:

Привязать Build, Run, Test, Format, подготовку зависимостей и операции изменения Git-дерева к проекту и зафиксированной версии.

Согласовать checkout/restore с автосохранением.

Считать результаты старой версии устаревшими и показывать это при необходимости.

Не применять форматирование или массовое изменение к уже изменённому исходнику.

Инвалидировать затронутые кеши и диагностику после смены ветки или зависимостей.

Приёмка:

Изменение файла во время длительной операции не позволяет её результату затереть новый текст.

Переключение проекта не переносит диагностику или результаты в другой проект.

Автосохранение предыдущего состояния не записывается поверх checkout.

Stop и последующий запуск используют корректные отдельные состояния.

Обычные remote cursor updates в Playground не становятся изменением исходной версии.

P0-04. Build без исполнения

Подтверждено исходниками. cargo build и cargo run направлены в один onRun(). ProjectTerminalSession.

Работа:

Разделить compile-only и compile-and-run в модели операции.

Оставить разрешённые build scripts самостоятельной стадией сборки.

Обновить журнал стадий, кеширование и статус результата.

Сохранить Check как отдельную операцию анализа.

Приёмка:

Программа с записью файла и маркером в stdout после Build не выполняет эти действия своего main.

Run выполняет программу и создаёт ожидаемый результат.

Разрешённый build script может выполняться на своей стадии; это не считается запуском main.

Повторная сборка использует допустимый кеш и сохраняет правильную идентичность результата.

Ошибки компиляции и выполнения различимы.

P0-05. Один и тот же допустимый файл на всех стадиях

Подтверждено исходниками. ProjectStore.validate проверяет пути и наличие entry, а writeSnapshot пишет все строки проекта. При чтении readFiles молча пропускает файл, если размер превышает LocalProjectLoader.maximumFileBytes, равный 2 MiB. Обычное изменение текста и autosave не применяют этот лимит симметрично. ProjectLibrary, LocalProjectLoader, CompilerViewModel, редактор.

Ожидаемый дефект. В проекте с небольшим main.rs увеличить вспомогательный notes.txt или .rs до размера больше 2 MiB. Текст может быть записан, а при следующем открытии исключён без ошибки, поскольку entry-файл остался. Аварийное восстановление, запускаемое на ошибке чтения, не обязано сработать при таком «успешном» неполном чтении. На устройстве этот сценарий в данном разборе не выполнялся.

Работа:

Определить общие бюджеты редактируемого проекта и форматов переноса.

Применять их к импорту, вставке, редактированию, терминальным изменениям, сохранению и чтению.

Не терять введённый текст при обнаружении превышения: сохранить доступную копию, предложить экспорт или уменьшение.

При чтении ранее сохранённого файла не считать его молчаливое исключение успешным восстановлением проекта.

Разделить большой непрозрачный файл репозитория и текст, который редактор действительно поддерживает.

Приёмка:

Файлы в пределах, на границе и выше 2 MiB не исчезают без сообщения.

Проверены вспомогательный файл, entry, вставка и замена файла из терминала.

Суммарный бюджет проекта учитывается на тех же стадиях.

Ошибка открытия сообщает точный путь и сохраняет возможность извлечь исходные данные.

Исправление не уменьшает заявленный поддерживаемый объём молча.

P0-06. Сохранение должно иметь видимый результат

Подтверждено исходниками. CompilerViewModel.remember вызывает try? await projectLibrary.record(...); этот маршрут подавляет ошибку записи и не переводит её в отдельное видимое состояние. CompilerViewModel.

Автосохранение с задержкой 500 ms, атомарная запись и предыдущий recovery snapshot уже реализованы. Их нужно сохранить. Здесь требуется дополнить их правильной реакцией на неудавшуюся запись.

Работа:

Различать unsaved / saving / saved / failed для конкретной версии проекта.

Считать версию сохранённой только после успешного завершения записи.

Сохранять актуальный текст в памяти при отказе.

Давать повтор записи и экспорт несохранённых изменений.

Не позволять успешной записи старой версии убрать статус ошибки или изменений более новой версии.

Приёмка:

Внедрённая ошибка записи приводит к видимому сообщению, а не к впечатлению успешного сохранения.

Пользователь сохраняет текущий текст повтором или экспортом.

Успешный retry обновляет именно подходящую версию.

Перезапуск и recovery сохраняют существующие гарантии; сообщение не обещает восстановить никогда не записанные байты.

DEBUG-01. Ресурсный макрос должен оставаться тем же макросом

Воспроизведено. Bundled transformer переписывает include_str!("main.rs") внутри программы с собственным macro_rules! include_str в вызов с именем generated sidecar. Трансформация выбирается по имени без доказанного разрешения builtin. Минимальный пример — приложение A.1. Instrumenter, bundle.

Работа: учитывать локальные определения, shadowing, imports и квалифицированные пути. Если безопасно определить смысл вызова невозможно, отказаться от этой формы Debug с объяснением, сохранив обычный Run. Простое совпадение последнего сегмента имени недостаточно. Rust macro scoping.

Приёмка:

Пользовательский include_str! / include_bytes! не получает другой строковый аргумент.

Стандартные resource macros продолжают сохранять исходные байты, включая source-as-data.

Относительные пути, raw strings, multiline paths и коллизии sidecar остаются покрыты.

Поддержанный случай имеет одинаковый наблюдаемый результат Run/Debug; неподдержанный определяется до вводящего в заблуждение выполнения.

DEBUG-02. Служебные имена не затеняют пользовательские

Воспроизведено. Для let s = String::from("x") создаётся preview(&s, |s| { ... Probe(&s) ... }). Внутри closure второй s означает generated Sink. Точный compiler diagnostic или отображение в приложении здесь не проверялись; обращение к неверному binding видно в фактически полученном коде. Instrumenter, checkpoint.

Работа: использовать гарантированно свободные имена для generated bindings и согласовать это с проверкой зарезервированного helper namespace. Одной замены s на другое короткое постоянное имя недостаточно.

Приёмка:

Обычный локальный s корректно отображается в Debug.

Проверены совпадения имён с внутренними переменными, nested scopes, raw identifiers и shadowing.

Generated guards не меняют доступность пользовательских bindings.

Проверены и общий TypeScript instrumenter, и заново собранный bundled JS.

DEBUG-03. Инструментирование учитывает перемещение значений

Воспроизведены два случая. После пользовательского println!(value), разворачивающегося в drop(value), остаётся injected preview value. То же происходит с обычным стандартным dbg!(value) для String. Стандартный dbg! принимает владение non-Copy аргументом; поэтому последующий borrow должен быть исключён. Добавление borrow подтверждено запуском instrumenter; фактический rustc diagnostic здесь не получен. Instrumenter, dbg!.

Работа:

Пересмотреть whitelist макросов, которые считаются не потребляющими значение.

Разделить dbg!(value) и dbg!(&value).

Не выводить ownership пользовательского макроса только из имени println.

Осторожно обрабатывать пользовательские типы и методы, похожие по имени на стандартные.

Сохранять краткоживущий borrow и ограниченные previews без вызова произвольного пользовательского Debug.

Приёмка:

Обычные String / Vec, перемещения, partial moves и mutable borrows сохраняют поведение.

Примеры из A.3 и A.4 проходят реальный normal/Debug compiler comparison либо получают обоснованную явную границу до трансформации.

Результат, stdout, stderr в заявленной части и созданные ресурсы проверяются по смыслу сценария; технические Debug-сообщения отделены.

Stop и новый Run работают после отказа.

Существующие ресурсы, async polling и compact gutter UI не регрессируют.

Порядок внутри Debug: сначала DEBUG-02 как случай с обычным именем, затем ownership стандартного dbg! и общая обработка shadowed macros. Подтверждённый общий дефект нужно исправлять в исходном instrumenter и пересобирать bundle; ручная правка только minified JS создаст расхождение app/browser.

6. RUST — тесты и форматирование

RUST-01. Пользовательский test runner

Проверяющие механизмы Academy уже существуют. Здесь добавляется проверка обычного пользовательского проекта. В просмотренном терминальном диспетчере cargo test не реализован. ProjectTerminalSession.

Сначала техническое подтверждение:

Проверить доступность и работоспособность rustc --test / libtest в выбранном bundled toolchain.

Определить поддерживаемую модель выполнения и ограничения потоков.

Раздельно описать unit tests, integration targets, dev-dependencies и doctests.

Если обычный harness не работает, зафиксировать причину и исследовать совместимый ограниченный режим. Не выдавать произвольную самописную проверку за полную совместимость Cargo.

Обычный Cargo создаёт тестовые исполняемые файлы через libtest; doctests используют отдельный путь через rustdoc. Это разные этапы совместимости. Cargo test.

Первый полезный объём:

Обнаружение и список поддерживаемых тестов.

Запуск одного теста и набора с фильтрацией.

Отчёт passed / failed / skipped / compile error / canceled.

Явно квалифицированное поведение #[should_panic], ignored tests и выбранного режима panic; отсутствие поддержки сообщается отдельно.

Assertion, stdout/stderr и переход к доступной позиции исходника.

Привязка результата к версии проекта.

Повторный запуск и Stop.

Приёмка:

Успешный, падающий, паникующий, ignored и зависающий тест обработаны корректно; #[should_panic] поддержан в заявленном режиме или явно обозначен как ограничение.

Ошибка компиляции не отображается как успешный тест.

Неподдерживаемый target или зависимость объясняются до ложного обещания выполнения.

Stop завершает выполнение, после чего можно запустить другой тест.

Подготовленный проект тестируется офлайн.

После изменения проекта старые результаты не выглядят актуальными.

Отдельный пользовательский test runner не нарушает проверки Academy.

RUST-02. Rust formatter

Работа:

Выбрать и закрепить поддерживаемый rustfmt либо эквивалентный реальный formatter, совместимый с архитектурой приложения.

Использовать bundled библиотечный или иной подтверждённый локальный путь; существование desktop CLI не означает возможности просто запустить его на iOS.

Учитывать edition и документированный набор конфигурации.

Поддержать форматирование файла, затем проекта.

Сохранить Undo, курсор и выделение насколько позволяет изменение.

Защититься от применения к устаревшему снимку.

Приёмка:

Повторное форматирование не меняет результат.

Ошибка разбора сохраняет исходный текст.

Undo возвращает предыдущий текст.

Проверены макросы, комментарии, Unicode, raw strings и поддерживаемые editions.

Форматирование проекта не меняет невыбранные служебные и dependency-файлы.

Действие работает без сети и не использует AI как источник «канонического» форматирования.

Clippy остаётся отдельной последующей возможностью. Его отсутствие не должно блокировать полезную первую версию тестов и форматирования.

7. GIT — локальная история и удалённые репозитории

7.1. Архитектурная основа

Текущий GitHub import получает архив исходников и сохраняет commit: nil. Это не перенос истории репозитория. GitHubProjectImporter.

Для Git нужен слой, сохраняющий полное допустимое содержимое репозитория, включая файлы, которые редактор не умеет изменять.

Предлагаемая модель:

Устойчивая идентичность проекта Crabrix.

Каноническое рабочее дерево и долговечное Git-хранилище.

Явное разделение исходников, непрозрачных файлов, метаданных Crabrix, кешей и подготовленных зависимостей.

Сервис операций Git, используемый и интерфейсом, и терминалом.

Согласованные операции изменения дерева через P0-03.

Учёт общего объёма репозитория отдельно от редактируемого набора файлов.

GIT-01. Локальный Git

Первый интерфейс: экран Changes внутри существующего проекта.

Функции:

Инициализация репозитория.

Status: modified / untracked / deleted.

Текстовый diff.

Выбор файлов для коммита.

Автор и сообщение коммита.

История и просмотр версии.

Восстановление файла с предварительным показом результата.

Создание и переключение ветки.

Понятное состояние незакоммиченных изменений.

Автосохранение продолжает защищать текущую работу. Оно не создаёт коммит на каждое изменение.

Миграция:

Для обычного проекта — инициализация новой истории.

Для старого ZIP-import с неизвестным commit — новая локальная история либо повторный clone исходного репозитория с явным переносом пользовательских изменений.

Не придумывать родительский commit и не обещать восстановление отсутствовавшей истории.

Исходную локальную копию сохранять до успешного завершения миграции.

Приёмка:

Коммиты и refs читаются стандартным Git после переноса.

Сохранение проекта Crabrix не удаляет Git objects/index/refs.

Скрытые конфигурационные файлы сохраняются.

Неизменённые бинарные и другие неподдерживаемые редактором файлы не превращаются в удаления.

Если репозиторий не укладывается в поддерживаемую модель, операция отказывается с объяснением до частичной замены.

Checkout учитывает незакоммиченную работу и не перетирает её молча.

История сохраняется после перезапуска и обновления приложения.

Смена ветки обновляет редактор, диагностику и состояние зависимостей.

Все локальные операции доступны без обязательного аккаунта.

GIT-02. Удалённые репозитории

Первый сетевой профиль:

Явное подключение поддерживаемого Git-хоста.

Fetch.

Fast-forward pull.

Push.

Текущая ветка, remote и ahead/behind.

Понятная обработка расхождения истории и отказов сервера.

Полноценные rebase, LFS, submodules, arbitrary hooks и широкая enterprise-аутентификация не обязательны для первого полезного выпуска. Неподдерживаемые требования должны распознаваться и объясняться.

Данные доступа:

Использовать защищённое хранилище платформы.

Не включать токены в проект, ZIP, Git-конфигурацию с открытым секретом, журналы, runtime или Playground.

Сохранять локальную работу при отзыве прав.

Не связывать локальные коммиты с обязательной регистрацией Crabrix.

Не запускать push автоматически от каждого совместного изменения исходника.

Приёмка:

Полный сценарий: clone → работа офлайн → commit → reconnect → push → продолжение той же истории на компьютере.

Проверен выбранный механизм доступа к приватному репозиторию.

Fetch не изменяет рабочие файлы.

Pull обновляет дерево только при выполнении заявленных условий.

Отказ push и diverged history сохраняют локальные коммиты.

Обрыв сети, нехватка места и отмена не оставляют существующий проект повреждённым.

Секреты не оказываются в экспортируемых и совместных данных.

Регрессии существующего GitHub snapshot import проверены отдельно.

14. LANG — C, Systems Lab и C++

14.1. Рекомендация по языкам

C стоит рассматривать раньше C++. Его первая полезная роль в Crabrix — ограниченная системная лаборатория рядом с Rust: память, представление данных, ownership и простой ABI. Это понятное продолжение существующей учебной идеи.

C++ пока остаётся условным этапом. Сначала нужны повторяющиеся пользовательские задачи, выбранный стандарт и проверенная цена поддержки библиотек, compiler/runtime и редактора. Просто увеличение числа языков не завершит текущие Test/Git/Debug-сценарии.

Добавление Git и добавление пользовательского C-компилятора — независимые решения. Даже если Git встраивается через C-библиотеку, пользовательская поддержка языка C для этого не требуется.

A.0. Что выполнено

В этом разборе в Node v24.22.1 исполнен точный Crabrix/Resources/RustDebugCompiler.js из проверенного commit. Локальные байты сверены с Git blob; для четырёх сценариев проверены фактически созданные фрагменты. Bundle.

Git blob: 7dead4c9d13e06e5ff6ce92c70363a41674b4b06.

Размер: 150 998 bytes.

SHA-256: d5c48bd5df83ef700ceb87df937e1cdbf1f08231465853984db078f0bf894628.

Выполнено: instrumentation и проверки generated Rust.

Не выполнено в этом разборе: Rust compilation, Wasm execution, Xcode, устройство.

Общий способ повторить трансформацию из корня checkout нужного commit:

const fs = require("node:fs");
const vm = require("node:vm");
const context = {};
vm.createContext(context);
vm.runInContext(
  fs.readFileSync("Crabrix/Resources/RustDebugCompiler.js", "utf8"),
  context
);

// Подставить один из исходников ниже.
const source = 'fn main(){let s=String::from("x");println!("{}",s);}';
const plan = JSON.parse(
  context.CrabrixRustDebugCompiler.instrument(
    JSON.stringify({ files: { "main.rs": source }, entryFile: "main.rs" })
  )
);
if (plan.error) throw new Error(plan.error);
console.log(plan.files["main.rs"]);

Это диагностический воспроизводитель, а не тест «правильности» дефекта: после исправления generated fragment должен измениться. Для закрытия задачи нужны дополнительные реальные Run/Debug comparisons.

A.1. Собственный include_str

macro_rules! include_str {
    ($x:literal) => { $x };
}
fn main() {
    println!("{}", include_str!("main.rs"));
}

Фактически получено:

println!("{}", include_str!("__crabrix_debug_original_1.txt"));

В исходной программе локальный макрос возвращает свой аргумент. Замена аргумента меняет её смысл; вывод о смене строки следует из Rust name resolution, но stdout компилятора в этом разборе не измерялся. Macro scoping.

A.2. Обычная переменная s

fn main() {
    let s = String::from("x");
    println!("{}", s);
}

Фактически полученный фрагмент:

preview(&s, |s| {
    use crate::__crabrix_debug_v1::Inspect as _;
    (&crate::__crabrix_debug_v1::Probe(&s)).inspect(s, 0);
})

Probe(&s) внутри closure обращается к служебному параметру. Точный diagnostic или неверное отображение нужно зафиксировать фактическим compiler/UI запуском.

A.3. Пользовательский println, перемещающий значение

macro_rules! println {
    ($x:ident) => { drop($x) };
}
fn main() {
    let value = String::from("x");
    println!(value);
}

После println!(value); transformer добавляет checkpoint с preview(&value, ...). Макрос раскрывается в перемещение value; последующий borrow должен быть исключён. Фактический compiler diagnostic здесь не получен.

A.4. Обычный dbg с owned String

fn main() {
    let value = String::from("x");
    dbg!(value);
}

После dbg!(value); также добавлен preview(&value, ...). Это уже случай со стандартным макросом. Документация dbg! подтверждает получение владения; для сохранения значения пользователь может писать dbg!(&value), но отладчик должен корректно обработать и исходную допустимую программу. dbg!.
